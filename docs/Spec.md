# Spare Parts Demand Forecasting & Firm Scheduling: SPEC v4.2 (FINAL, supersedes all earlier versions)

**Product:** AI-based spare-parts demand forecasting and firm scheduling system for a manufacturing organization, with a controlled multilingual "Ask AI" assistant.
**Stack:** React + TypeScript, Django + Django REST Framework + SimpleJWT, one Python package for forecasting/scheduling/simulation (`ml/`), one relational database (SQLite in dev; MySQL or Postgres by environment variable). No second backend, no queue, no extra services.
**Sources of truth:** the problem-statement PDFs (original requirements plus the updated multilingual/agentic requirements), the MVP brief, the three CSVs, `generate_datasets.py`, `validate_datasets.py`. If a file disagrees with this spec, report the discrepancy and follow the verified file.
**Goal:** Right Part + Right Quantity + Right Time + Right Inventory, shown by measured KPIs on synthetic data. Always say "method validated on simulated data", never "proven savings".
**Change control:** v4.2 consolidates v4.1, the MVP alignment amendment (Appendix C of the earlier draft) and the Phase 5 closure findings. Log "v4.2 consolidation" and its reason in `STATE.md`. Any later change needs a logged reason. On 2026-11-16, an explicitly approved Phase 5 data-limitation exception was added without broadening the donor rule; see section 12, Phase 5(c), and the corresponding `STATE.md` entry.

## 4. Architecture, efficiency, security
**Architecture.** `backend/` Django + DRF + SimpleJWT (apps `accounts`, `planning`, `assistant`); `ml/` plain Python (data, features, forecasting, scheduling, simulation, evaluation, classification), imported directly by Django; `frontend/` React + TS with hooks (no Redux, no SSR); `configs/` holds every business parameter (weights, gates, costs, service targets, horizon, languages, latency budget, frozen-window length). Data is read through one schema-validated loader.

**Efficiency and scale.** Forecasts, schedules, KPIs and warnings are batch jobs (Django management commands) that save versioned results; dashboards read saved results only. Only `propose_change` computes live (budget in config, default 5 s). Paginate every list; index part, region, week and `run_id`; `select_related`/`bulk_create`; Parquet for large intermediate tables; lazy-load pages and virtualize long tables. Stateless API (more workers can sit behind one reverse proxy). Caching only for endpoints measured slow, with an invalidation rule. No Redis/Celery/Kubernetes unless measured need. Record batch runtime and endpoint latency in `results/performance_log.csv`.

**Run management.** Every forecast/schedule run writes a `runs` record: `run_id`, timestamp, data version (file hash), config version (hash), model version, horizon, scheduling policy, checker version, status, duration, error, output location. The API serves a forecast and a schedule only together under one `run_id`. Retraining is offline; a new model is promoted only after beating the current champion on the fixed validation benchmark. Nothing changes live.

**Security (each item has a test).**
- Auth: server-side permission on every endpoint and object. Roles viewer (read), planner (propose), approver (confirm), admin. Planners cannot confirm. Short token expiry, refresh, logout revokes tokens, Django password validators.
- Hardening: `DEBUG=False`, explicit `ALLOWED_HOSTS`, narrow CORS/CSRF origins, HTTPS and secure cookies in production, security headers, secrets only in environment variables, locked `requirements.txt`, `pip-audit` before release.
- Input: DRF serializers validate type, range, ID and size on every body; ORM only, no string-built SQL. Rate limits on login, Ask AI and `propose_change`.
- AI isolation: prompts, imported data and model replies are untrusted. The model has no database access and cannot bypass the scheduling engine; it only produces typed intents; the server re-validates part IDs, quantities and permissions. No credentials or unnecessary business data go to an external provider. On parse failure, timeout or ambiguity: ask for clarification or use the rule-based fallback.
- Proposal lifecycle: a proposal records the schedule version it was calculated on and has its own version. Confirmation is valid only if (a) both versions still match, (b) it has not expired (default 60 minutes), (c) the confirming user holds the approver role now, (d) the approver is not the proposer (`allow_self_approval=false`; if enabled it is flagged in the audit entry). If the schedule changed, the proposal becomes `stale` and must be recalculated. Apply in one transaction; reject duplicates; idempotency key on retries; concurrent edits tested. A revert is a new, separately authorized change linked to the original audit entry, allowed only if the schedule has not changed since; original entries are never edited or deleted.
- Audit: append-only through the API; records who proposed, approved and applied, before/after values, validation results, timestamps; secrets redacted.
- Backup: documented backup and a restore test with integrity checks.
This is a strong student-project baseline, not a substitute for a professional security review.

## 5. Forecasting
**Required set (Phases 3 and 4, done):** naive; seasonal naive; one intermittent baseline (TSB chosen); global LightGBM point (Tweedie chosen); LightGBM quantile (P50, P90, P95, P99); equal-weight ensemble. Every run, including failures, stays in `results/track_a_candidates.csv`. Tuning: same fixed budget per model, tuning origins only, seed 42.
**Roles.** The point forecast drives netting, MRP and KPIs. The quantile forecast drives safety stock and early warnings; it is judged on coverage and pinball loss and on P50 for point metrics, never on signed bias. Quantiles must not cross (P50 <= P90 <= P95 <= P99; sort or apply a documented correction).
**Features (16 PDF factors only):** lags 1/4/13/52; rolling mean/median/std from past values; week, month, fiscal calendar; festival flag and weeks-to-festival; holiday, shutdown, working days; published promotions/campaigns; region, category, criticality, ABC, fulfilment mode, part type; vehicle type/model seasonality; zero-run length and time since last demand; obsolete flag only from lifecycle.
**Metric definitions (ratios internally; percent only for display).**
- WAPE = sum|A - F| / sum A; if sum A = 0 report "undefined", exclude from averages, never 0.
- Signed bias = (sum F - sum A) / sum A (positive = over-forecast). Asymmetric bias = |bias| if bias >= 0, else `under_weight` x |bias| (configurable scenario, default 2).
- MASE scales by the in-sample one-step naive error of the training period (undefined for all-zero training series; excluded and counted).
- Lead-time demand = sum of weekly forecast and actual over ceil(lead time in days / 7) weeks from the origin; lead-time WAPE compares those sums. Lead times above 14 weeks use the 14-week horizon plus the last-four-week mean extension (labelled).
- Forecast Accuracy % = 100 x (1 - WAPE), always shown beside WAPE; it can go negative and is not a probability. API fields carry units (`wape_ratio`, `accuracy_pct`).
- Forecast-vs-actual variance = signed and absolute difference per part and period. MAE and RMSE are reported, not scored. MAPE is reported only on non-zero actuals with the excluded count shown and labelled unreliable (about half of weekly values are genuine zeros).
- Coverage = share of actuals at or below the quantile, by criticality and horizon with sample counts ("insufficient data" below 30).
- Every metric is reported weekly and lead-time aggregated, overall and by SBC class, ABC, criticality, region, category and horizon step. Lead-time results and intermittent-series service outcomes take precedence when they disagree with weekly WAPE.

## 6. Selection and weights (editable assumptions)
**Three steps.** (1) Screening rules with bootstrap intervals (resample series and origins together): beats seasonal naive and historical average on lead-time WAPE (enforced); overall |bias| <= 10%; critical under-forecast bias no worse than -10%; for quantile models P95 coverage within +/-5 points on critical parts (the last three flagged, not rejected, when the interval includes the threshold; set `gates.enforce`). Evidence inconclusive means keep the simpler model; never say "significant" without interval support. (2) Weighted score among eligible models (rank normalization; ties on simplicity, explainability, runtime). (3) Perturb each weight by +/-10 points; if the top model wins at least 75% of perturbations it is the champion, otherwise report contenders and break the tie by downstream simulation (service level and cost on the validation period).
**Track A:** overall error (70% lead-time, 30% weekly) 20; critical/A-class error 20; intermittent/lumpy (lead-time WAPE and MASE) 15; asymmetric absolute bias 15; calibration (coverage error + pinball; no quantiles = minimum) 15; stability across origins 10; runtime and explainability 5 (total 100). Asymmetric bias appears in two components on purpose; report the overlap-removed scenario.
**Track B:** critical-part availability 25; overall fill rate/stock-out % 15; emergency procurement 15; excess inventory and carrying cost 20; schedule adherence and stability 15; turnover 10 (total 100). A hard-constraint violation disqualifies a scheduler.
**Track C:** intent accuracy 25; entity accuracy 25; rule-validation correctness 20; multilingual consistency 15; audit completeness 10; latency/cost 5. Disqualifiers: change applied without confirmation, invented quantity.
**Business defaults** (`configs/business.yaml`, until the business team replies): priority per section 2; service targets from D2 `service_level_target` (never invented); emergency cost = unit cost x 1.5 (test 1.25 to 2.0); stock-out penalty = unit cost x 10/5/2 for High/Medium/Low criticality (vary +/-50%); carrying cost from D2 rate (25% annual fallback only if absent); downtime cost not measurable. Report whether winners change across these ranges.

## 7. Scheduling contract (one convention for scheduler and simulator)
- Time unit: week; week 1 is the first planning week.
- **Order of operations each week:** receive scheduled deliveries; add to opening stock; allocate stock to existing backlog (High-criticality parts) then current demand; record fulfilled quantity and the remainder as backlog (High criticality, carried forward) or lost sales (others); reconcile `Closing = Opening + Receipts - Fulfilled`. Closing stock is never negative. Receipts due in week t arrive at the start of week t, before demand.
- **Timing:** an order released at the start of week r arrives at week r + max(1, ceil(lead time days / 7)) (deliberately conservative; one convention everywhere). Release is not earlier than week 1. Tested: 1 day gives r+1, 7 days r+1, 8 days r+2, 14 days r+2. Orders arriving after week 14 are kept, flagged `arrives_beyond_horizon`, not counted as in-horizon supply. An order that cannot arrive in time is reported late, not hidden.
- Order quantity = max(net requirement, MOQ), rounded up to the order multiple.
- Usable stock = on-hand - reserved - blocked, checked against `available_qty`. Open POs (due this month plus due later) and in-transit are counted once. D2 has no pending-requirement column: D2 backorder is the labelled assumption (High-criticality backlog; Medium/Low written off).
- **Reorder point:** computed ROP = lead-time point demand + safety stock; D2 `current_reorder_point_qty` defines the current-policy baseline (order up to target when available + on-order <= D2 ROP). Report computed vs D2 ROP gap per part.
- **Safety stock:** smallest available forecast quantile at or above the part's service target (cap P99), over the lead-time window; safety stock = max(0, lead-time quantile demand - lead-time point demand); regional and weekly quantiles are summed (conservative; label it). Optional per-quantile calibration multiplier fit on tuning-origin forecasts only, OFF by default, enabled only if High-criticality service misses target in simulation; report both runs.
- **Supplier risk (MVP requirement):** planning lead time = D2 lead time + expected delay (late share x average delay days); order quantity is grossed up by 1/(1 - rejection share) before MOQ/multiple rounding; suppliers below a configurable reliability threshold (default lowest quartile, assumption) raise a warning. `supN_reliability_pct` is never applied as a separate probability (it overlaps OTD and rejection). The simulator keeps its own seeded delay and rejection draws.
- **SOB** is an allocation target (D2 shares sum to 100; the generator uses them as load weights, not a contract). Report realized deviations; they are not hard failures.
- **Capacity:** `supN_monthly_capacity x (1 - committed_pct/100)` in order-quantity units per calendar month. One-pass pull-ahead may release earlier (never before week 1) to use earlier-month capacity before a plan is marked unresolved.
- **Frozen window (planning time fence):** orders in the first N weeks (config, default 2) are frozen; changes inside the window need an approver and show a warning. Schedule stability (nervousness) is measured as order changes inside the window between replans.
- `firm` = every hard constraint passed by the independent checker (MOQ, multiple, capacity, lead time, non-negative stock, no new orders for obsolete parts, no import supplier for production parts). Anything else is `unresolved` with `failed_checks` that distinguish `release_before_week_1` (lead-time infeasible), `supplier_capacity` and `moq_multiple_rounding`. Never replace an infeasible result with arbitrary quantities. Preserve feasible partial allocations.
- Emergency supply: triggered only when High-criticality backlog remains at week close; exact remainder received next week; outside the schedule (excluded from the schedule checker, logged separately by count, quantity and cost); cost = unit cost x 1.5. Stock-out is measured at week close before the emergency receipt. Same rules for every policy.
- Scheduling is part-level (D2 has one row per part); the schedule's region/plant column is `ALL`.
- Call the output a **simulated firm schedule** in the report and UI.

**Simulator initialization (replaces the D2-snapshot rule as primary).** D2 stock, POs and backorders are dated 2026-09-26, after every validation origin, and median cover against validation demand was about 0.5 weeks, so a D2-based start mostly measures the starting point. Primary rule, origin-visible and identical for every policy: opening available stock = ceil(trailing 13-week mean weekly demand, observed complete weeks visible at the origin, at least 8 weeks else flag/exclude the path) x (ceil(SOB-weighted lead time days / 7) + 1) weeks; opening open POs and backlog = 0. Keep the D2-snapshot start as a labelled stress scenario (`d2_snapshot_stress`). Report initial cover for both. Demand paths use only complete observed validation actuals aggregated over regions; exclusions are reported by reason and segment.

**Hand-calculated tests (before any scheduler comparison):** (1) enough stock, no order; (2) shortage covered by a timed receipt; (3) order missing its date because of lead time; (4) MOQ and multiple rounding; (5) capacity exhausted; (6) obsolete part gets no order; (7) backorder/open PO not double counted; (8) lead times of 1, 7, 8, 14 days plus a beyond-horizon case; (9) critical part with backlog and insufficient stock (backlog first, remainder carried); (10) ordinary part, same situation (remainder lost). Plus: inventory conservation, determinism for seed 42, the checker rejecting invalid schedules, config-hash and duplicate-YAML-key guards.

## 10. Part classification (MVP requirement; Phase 8A)
Train a classifier that predicts part category from part information, excluding the category field itself (TF-IDF character n-grams on name/component/material with logistic regression, or sentence embeddings).
